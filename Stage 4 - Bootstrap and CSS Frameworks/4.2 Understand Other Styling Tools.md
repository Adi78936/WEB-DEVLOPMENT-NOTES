# 4.2 Understand Other Styling Tools

## Interview preparation

Styling tools provide different ways to author, organize, and reuse CSS. Choose based on the project, team, design system, runtime, and maintenance requirements—not popularity alone.

## What is Tailwind CSS?

Tailwind CSS is a utility-first CSS framework. It provides low-level utility classes for styling elements directly in markup, such as spacing, layout, color, and responsive states.

```html
<button class="rounded-md bg-emerald-800 px-4 py-2 text-white hover:bg-emerald-900">
  Prepare image
</button>
```

Tailwind versions differ in installation, configuration, theme customization, and build behavior. Follow the documentation for the project’s installed version.

## Utility-first CSS

In a utility-first approach, small classes represent individual style decisions:

```html
<div class="flex items-center gap-3 p-4">
  <span class="font-medium">Preview ready</span>
</div>
```

Advantages:

- The styling is visible near the markup it affects.
- Existing utilities can support consistent spacing and values.
- Responsive and interaction states can be expressed locally.
- Build tooling can generate only the styles identified in the project source.

Trade-offs:

- Long class attributes can be difficult to scan.
- Shared patterns still need component or abstraction decisions.
- Team members must understand the project's utility conventions.
- Custom styling may still require CSS or theme configuration.

Utility-first is a way to author styles; it does not mean that semantic HTML or reusable components are unnecessary.

## Tailwind installation

For a new project:

1. Check the official Tailwind guide for the framework and build tool in use.
2. Install the version and packages prescribed by that guide.
3. Configure the CSS entry point and any required build integration.
4. Import the generated stylesheet in the application.
5. Verify production builds include the expected classes.

Tailwind's setup differs substantially between major versions. Do not copy an old configuration file, directive, or plugin setup into a newer release without checking compatibility.

## Responsive utility classes

Responsive prefixes apply a utility at and above a breakpoint in Tailwind's mobile-first model:

```html
<div class="grid grid-cols-1 gap-4 md:grid-cols-2 xl:grid-cols-3">
  ...
</div>
```

This is a conceptual example; exact utilities and breakpoint customization depend on the Tailwind version/configuration.

- Unprefixed utilities generally form the base style.
- A breakpoint-prefixed utility applies from that breakpoint upward.
- Breakpoint labels are configurable and are not guarantees about specific device models.

## Hover, focus, and other states

State variants apply utilities in interaction or accessibility states:

```html
<button class="bg-emerald-800 hover:bg-emerald-900 focus-visible:outline-2">
  Continue
</button>
```

- Provide a visible keyboard focus state, not just hover feedback.
- Hover is not available on all devices; important behavior must not depend on it.
- Include disabled, selected, active, and error states when relevant.
- Prefer native controls and semantic markup over simulated behavior built from styles alone.

## Dark mode

Dark mode can be driven by system preference or an explicit application theme, depending on framework configuration:

```html
<div class="bg-white text-slate-900 dark:bg-slate-900 dark:text-slate-100">
  Theme-aware content
</div>
```

Configure how the `dark` variant is activated in the installed Tailwind version. A manual theme toggle must update the actual theme state consistently. Test contrast, form controls, images, and focus indicators in both themes.

## Custom theme configuration

Tailwind exposes theme tokens through its version-specific configuration or CSS-based theme facilities:

```css
/* Illustrative token idea; exact syntax depends on the Tailwind version. */
:root {
  --color-brand: #285d4b;
  --radius-card: .75rem;
}
```

Define project-specific colors, spacing, fonts, and breakpoints centrally when shared values should remain consistent. Reuse semantic tokens such as “brand” or “surface” rather than scattering uncoordinated color values.

## Reusable component styling

Repeated class sequences can be kept maintainable through:

- Framework components, such as a shared React `Button`.
- Small semantic CSS classes for stable repeated patterns.
- Template/component composition.
- Carefully designed helper functions or class-merging utilities when the project needs them.

Do not create abstractions for every one-off group of classes. Extract a reusable component when the markup or behavior repeats and the abstraction has a clear responsibility.

## Tailwind with React

In React, utility classes are commonly written in the `className` prop:

```jsx
function Button({ children }) {
  return (
    <button
      type="button"
      className="rounded-md bg-emerald-800 px-4 py-2 font-medium text-white hover:bg-emerald-900 focus-visible:outline-2">
      {children}
    </button>
  );
}
```

- JSX uses `className` rather than the HTML `class` attribute.
- Keep components semantic and type their props in TypeScript projects.
- If conditional styling uses classes, verify that the build tool can detect the possible class names. Dynamically assembled strings may not be recognized by scanning-based generation.
- Avoid putting user-provided, untrusted strings directly into generated class names.

## CSS vs. Bootstrap vs. Tailwind

| Approach | How styles are authored | Good fit when | Trade-offs |
|---|---|---|---|
| Plain CSS | Rules, selectors, custom properties, and media queries | The interface needs custom design, low dependency overhead, or a team prefers explicit stylesheets | Requires naming conventions and design-token discipline |
| Bootstrap | Prebuilt components, grid, utilities, and optional JS plugins | A team needs a broad component toolkit and consistent, familiar defaults quickly | Default visual identity can be recognizable; overrides and unused styling may accumulate |
| Tailwind CSS | Utility classes composed in markup, with a configurable design system | A team prefers local styling, utility composition, and a token-driven implementation | Markup can become dense; version-specific tooling and component reuse need care |

These approaches can coexist, but avoid competing sources of truth. For example, loading both Bootstrap and a large custom utility system can add style conflicts and unnecessary CSS.

### Choosing between them

Ask:

1. Does the project have an existing framework or design system?
2. Does it need prebuilt interactive components?
3. How much brand customization is required?
4. What build tooling and CSS skills does the team already use?
5. How will responsive states, accessibility, and themes be maintained?
6. What is the cost of the dependency and generated CSS?

No tool is automatically best. For a small bespoke interface, plain CSS with design tokens can be sufficient. Bootstrap can accelerate common UI patterns. Tailwind can suit component-driven projects that favor utility composition.

## Common interview questions

1. **What does utility-first mean?**  
   Styles are composed from small single-purpose utility classes rather than being authored primarily as component-specific selectors.

2. **Does Tailwind eliminate CSS?**  
   No. It changes how many styles are authored; custom CSS and CSS fundamentals remain useful.

3. **How do responsive Tailwind classes usually work?**  
   Base utilities apply by default, while breakpoint-prefixed variants apply at and above configured breakpoints.

4. **How do you keep a repeated Tailwind pattern reusable?**  
   Use a component or composition when the markup/behavior repeats; use a clear CSS class or shared abstraction where appropriate.

5. **How do you choose CSS, Bootstrap, or Tailwind?**  
   Based on the existing stack, product design needs, team conventions, component requirements, customization, accessibility, and maintainability.

6. **Can Tailwind classes replace semantic HTML?**  
   No. Classes style elements; semantic HTML communicates content meaning and native behavior.

## Good practices

- Learn core CSS before relying on framework classes.
- Use the installation and configuration guidance for the exact framework version.
- Centralize the design tokens that should remain consistent.
- Make interactive states—including keyboard focus—explicit.
- Build reusable components when repeated markup and behavior justify them.
- Avoid layering multiple frameworks without a clear reason.
- Check production output, responsive behavior, accessibility, and theme contrast.
