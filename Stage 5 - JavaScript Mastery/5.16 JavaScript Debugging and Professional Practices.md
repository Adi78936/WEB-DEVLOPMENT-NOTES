# 5.16 JavaScript Debugging and Professional Practices

## Console debugging

Useful console methods:

```js
console.log(value);
console.info("Loaded");
console.warn("Unexpected state");
console.error(error);
console.table(records);
console.time("operation");
console.timeEnd("operation");
```

Log enough context to investigate a problem, but do not expose secrets, credentials, personal information, or large sensitive payloads.

## Breakpoints

Browser developer tools allow breakpoints in source code:

- Set a line breakpoint to pause before executing a line.
- Inspect local variables, closure values, and the call stack.
- Step over, into, or out of function calls.
- Use conditional breakpoints for a specific state.
- Inspect network requests and their response details in the Network panel.

Source maps can connect built/minified code to its original source when configured correctly.

## `debugger` statement

```js
function processImage(image) {
  debugger;
  return prepare(image);
}
```

When developer tools are open, `debugger` can pause execution. Remove intentional debugging statements before release unless they are part of a deliberate debugging workflow.

## Stack traces and reading errors

A stack trace describes the sequence of calls leading to an error. Read it from the error message and first relevant application frame, then follow the call chain.

Common error categories:

- `SyntaxError`: code cannot be parsed.
- `ReferenceError`: a binding is missing or accessed before initialization.
- `TypeError`: a value does not support the operation being attempted.
- `RangeError`: a value is outside an allowed range.
- Network/API failures: inspect request URL, status, headers, timing, and body.

The first visible error may cause later errors; fix the earliest meaningful failure before diagnosing downstream symptoms.

## Strict equality

Prefer `===` and `!==` to avoid implicit type conversion:

```js
if (status === "ready") {
  render();
}
```

Use coercive equality only when its behavior is deliberate, documented, and understood. Static analysis tools can enforce consistent rules.

## Defensive programming

Defensive code checks assumptions at trust boundaries:

```js
function getDisplayName(user) {
  if (!user || typeof user.name !== "string") {
    return "Unknown user";
  }
  return user.name;
}
```

Good defensive programming:

- Validates external/API/user data.
- Handles expected failure conditions explicitly.
- Uses useful fallbacks only when they preserve correct behavior.
- Avoids broad catches that hide bugs or convert failures into fake success.
- Does not add redundant checks for impossible conditions without a reason.

## Modular, readable code

- Give functions and variables intention-revealing names.
- Keep modules focused and dependencies clear.
- Avoid oversized functions and hidden side effects.
- Extract shared logic when it genuinely improves reuse or consistency.
- Use linting and formatting tools adopted by the project.
- Write tests for important behavior and edge cases.

## Error boundaries at application level

In UI frameworks such as React, an **error boundary** can catch certain rendering/lifecycle errors in a subtree and display fallback UI. It is not a JavaScript language feature and does not catch every error:

- It generally does not catch errors in event handlers, asynchronous callbacks, or server-side code by itself.
- Handle rejected Promises and event-handler errors explicitly.
- Provide recovery or reload actions where appropriate.
- Log diagnostic details safely; do not expose internal stack traces to users.

## Memory-leak fundamentals

JavaScript memory is garbage-collected, but objects remain live while reachable from references. Common accidental retention sources:

- Long-lived event listeners that retain closures.
- Timers or intervals that are not cleared.
- Observers that are not disconnected.
- Detached DOM nodes retained in arrays or caches.
- Unbounded caches or collections.
- Closures that keep large data reachable.

Clean up resources when components or pages are disposed:

```js
const controller = new AbortController();
window.addEventListener("resize", onResize, { signal: controller.signal });

// When the feature is disposed:
controller.abort();
```

Other cleanup methods include `removeEventListener`, `clearTimeout`, `clearInterval`, `observer.disconnect()`, and `worker.terminate()`.

## Debugging workflow

1. Reproduce the issue consistently.
2. Read the exact error and identify its first relevant application frame.
3. Inspect the inputs, current state, and network activity.
4. Form a specific hypothesis and test it with a breakpoint or minimal logging.
5. Fix the root cause rather than masking the symptom.
6. Add or update a test for the failure case.
7. Re-run relevant checks and remove temporary logs/breakpoints.

## Interview review

1. How use a breakpoint? Pause execution and inspect state/stack at a chosen point.
2. What is a stack trace? A record of calls leading to the current error or execution point.
3. Why prefer strict equality? It avoids implicit coercion.
4. Does a React error boundary catch Promise errors? Not generally; async failures need explicit handling.
5. Why can event listeners cause memory leaks? A long-lived target can retain a callback and its closed-over objects.
6. What should happen after reproducing a bug? Investigate root cause, fix it, add regression coverage, and rerun checks.

## Good practices

- Prefer reproducible evidence over guesses.
- Handle failures explicitly; do not silently return success-shaped data.
- Keep logs useful but free of secrets and personal data.
- Clean up listeners, timers, observers, and workers.
- Add regression tests for fixed bugs.
- Remove temporary debugging code before delivery.
