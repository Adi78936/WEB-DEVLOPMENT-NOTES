# 5.12 Asynchronous JavaScript

## Synchronous vs. asynchronous

Synchronous work executes in order and blocks the current JavaScript thread until it finishes. Asynchronous operations let the program continue while waiting for work such as timers, user input, or network responses.

JavaScript execution in a browser is usually single-threaded on the main thread, but the runtime coordinates asynchronous operations and other threads/APIs.

## Call stack, queues, and event loop

- **Call stack:** active synchronous function calls.
- **Task queue (macrotask queue):** tasks such as many timer callbacks and event callbacks.
- **Microtask queue:** promise reactions and `queueMicrotask()` callbacks.
- **Event loop:** coordinates when queued work can run after the current stack finishes.

After a task completes, the runtime generally drains microtasks before selecting another task. Rendering and exact scheduling have host-specific details, but promise callbacks normally run before a later timer task.

## Timers

```js
const id = setTimeout(() => console.log("Later"), 100);
clearTimeout(id);

const intervalId = setInterval(updateClock, 1000);
clearInterval(intervalId);
```

Timers schedule callbacks no earlier than a requested delay; they are not precise clocks and can run later due to workload or browser throttling. Avoid overlapping long work in an interval.

## Callbacks and callback hell

A callback is a function passed to an operation and invoked later:

```js
readFile(path, (error, data) => {
  if (error) return handleError(error);
  process(data);
});
```

Deeply nested callbacks make sequencing and error handling difficult (“callback hell”). Promises and `async`/`await` can make asynchronous flows easier to read.

## Promises and states

A Promise represents the eventual result of an asynchronous operation:

- `pending`
- `fulfilled` with a value
- `rejected` with a reason

A promise settles once; it cannot switch from fulfilled to rejected or vice versa.

## `then`, `catch`, and `finally`

```js
fetchData()
  .then(data => transform(data))
  .catch(error => report(error))
  .finally(() => hideSpinner());
```

- `then()` registers fulfillment and optionally rejection handlers; it returns a new promise.
- `catch()` handles rejection and is shorthand for a rejection handler.
- `finally()` runs after settlement; it usually preserves the previous result/reason unless it throws or returns a rejected promise.
- Throwing inside a handler rejects the promise returned by that chain.

## Promise chaining

Return the next promise/value from a handler so the chain waits and passes its result along:

```js
getUser()
  .then(user => getProjects(user.id))
  .then(projects => render(projects));
```

Forgetting `return` can make a later handler run before nested asynchronous work finishes.

## Promise combinators

- `Promise.all(iterable)`: fulfills when all fulfill; rejects as soon as one rejects. Results preserve input order.
- `Promise.allSettled(iterable)`: waits for every promise and returns each outcome.
- `Promise.race(iterable)`: settles with the first promise to settle.
- `Promise.any(iterable)`: fulfills with the first fulfillment; rejects with `AggregateError` if all reject.

An empty iterable has defined immediate outcomes that differ between combinators; check documentation when that edge case matters.

## `async` and `await`

```js
async function loadProject() {
  const response = await fetch("/api/project");
  return response.json();
}
```

- Calling an `async` function always returns a Promise.
- `await` pauses that async function until the value settles; it does not block the entire JavaScript thread.
- Awaiting a non-promise resolves to that value.
- Rejections become thrown errors at the `await` expression.
- Use `try...catch` around awaited operations when recovery or context is useful.

## Error handling

```js
async function loadData() {
  try {
    return await fetchData();
  } catch (error) {
    report(error);
    throw error; // Rethrow if callers must also know the operation failed.
  } finally {
    hideSpinner();
  }
}
```

Avoid silently converting failures into success-shaped empty data unless that is an intentional, documented behavior. Handle errors at an appropriate boundary and provide useful user feedback.

## Interview review

1. What is the microtask queue used for? Promise reactions and other microtasks, generally processed after the current stack and before the next task.
2. Does `await` block JavaScript's main thread? No; it pauses the async function and allows the runtime to process other work.
3. `Promise.all` vs. `allSettled`? Fail-fast rejection vs. wait for every result.
4. `race` vs. `any`? First settlement vs. first fulfillment.
5. Why return a promise inside `.then()`? To link its completion and value/rejection into the chain.
6. What does `finally` receive? It runs without receiving the fulfillment value or rejection reason as arguments.

## Good practices

- Handle rejected promises.
- Use `Promise.all` only when parallel operations are appropriate.
- Use `allSettled` when all independent outcomes matter.
- Do not assume timer delays are exact.
- Show loading and error states for asynchronous UI operations.
- Avoid swallowing failures or creating misleading fallback success.
