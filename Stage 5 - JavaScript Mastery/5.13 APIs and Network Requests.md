# 5.13 APIs and Network Requests

## What is an API?

An API (Application Programming Interface) is a defined contract through which software components communicate. A web API commonly exposes HTTP endpoints that accept requests and return responses, often with JSON data.

An API is not necessarily a database; it may validate, calculate, aggregate, or coordinate data from multiple services.

## JSON

JSON (JavaScript Object Notation) is a text data format commonly used for web requests:

```json
{"name":"Image workspace","ready":true,"count":3}
```

### Parse and stringify

```js
const data = JSON.parse('{"ready":true}');
const json = JSON.stringify({ ready: true });
```

- `JSON.parse()` converts valid JSON text to a JavaScript value and throws on invalid JSON.
- `JSON.stringify()` serializes supported values to JSON text; functions and symbols are omitted in objects, and unsupported values can serialize unexpectedly or cause errors.
- JSON has no native representation for `undefined`, functions, symbols, BigInt, or object references/cycles.

## Fetch API

`fetch()` returns a Promise for a `Response`:

```js
const response = await fetch("/api/projects");
```

Important: `fetch()` normally **does not reject** merely because the server returned an HTTP error status such as 404 or 500. Check `response.ok` or `response.status`.

```js
async function loadProjects() {
  const response = await fetch("/api/projects");
  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }
  return response.json();
}
```

Reading the body, such as `response.json()`, is asynchronous and can itself fail if the body is invalid or unavailable. A response body is generally consumable once; clone it if it must be read more than once.

## HTTP methods

- **GET:** retrieve a resource; parameters often appear in the URL.
- **POST:** submit data or ask the server to process/create something.
- **PUT:** commonly replace a resource at a known URL.
- **PATCH:** commonly update part of a resource.
- **DELETE:** request resource removal.

The API defines exact semantics. Use appropriate methods, and do not assume method choice is a security control.

## Sending headers and request bodies

```js
const response = await fetch("/api/projects", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Accept": "application/json"
  },
  body: JSON.stringify({ name: "Study project" })
});
```

- `Content-Type` describes the request body format.
- `Accept` describes response formats the client can process.
- JSON request bodies usually need `JSON.stringify`.
- Do not manually set `Content-Type: multipart/form-data` when sending `FormData`; the browser supplies the boundary.
- Secrets embedded in frontend JavaScript are visible to users. Use an appropriate backend flow for confidential credentials.

## Response status codes

Common status codes:

- `200 OK`: request succeeded.
- `201 Created`: resource created.
- `204 No Content`: succeeded without a response body.
- `400 Bad Request`: invalid request.
- `401 Unauthorized`: authentication is needed or invalid.
- `403 Forbidden`: the request is understood but not authorized.
- `404 Not Found`: resource not found.
- `429 Too Many Requests`: rate limited.
- `500`–`599`: server-side failure.

Applications should interpret status codes according to the API contract rather than assuming every response includes JSON.

## Handling errors and loading states

```js
async function refresh() {
  setState({ status: "loading" });
  try {
    const response = await fetch("/api/projects");
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const projects = await response.json();
    setState({ status: "success", projects });
  } catch (error) {
    setState({ status: "error", message: "Could not load projects." });
    console.error(error);
  }
}
```

Provide explicit loading, success, empty, and error states. Preserve actionable details without showing sensitive implementation data to users.

## CORS fundamentals

**Cross-Origin Resource Sharing (CORS)** is a browser-enforced mechanism that controls whether frontend JavaScript from one origin can access a response from another origin.

- An origin consists of scheme, host, and port.
- A cross-origin request may be sent, but the browser prevents JavaScript from reading the response unless the server returns appropriate CORS headers.
- Some requests cause a **preflight** `OPTIONS` request, especially when using certain methods, headers, or content types.
- CORS is enforced by browsers; it is not an authentication or authorization mechanism and does not prevent non-browser clients from making requests.
- The server must configure allowed origins/methods/headers. Frontend code cannot fix a server's missing CORS permission.
- Do not use wildcard origins with credentialed requests. Credentialed CORS requires explicit origin and credential configuration.

## Interview review

1. What does `fetch()` return? A Promise that resolves to a `Response`, including for HTTP error statuses.
2. How check for an HTTP error? Inspect `response.ok` or status and handle it.
3. What is JSON? A text-based data interchange format.
4. Does CORS authenticate users? No; it is a browser access-control mechanism.
5. What is preflight? A browser `OPTIONS` check before certain cross-origin requests.
6. Why not set multipart content type manually? The browser must add the correct multipart boundary.

## Good practices

- Check `response.ok` before treating a fetch as successful.
- Handle body parsing failures and non-JSON responses.
- Use loading, empty, success, and error states.
- Keep server credentials out of public frontend code.
- Configure CORS on the server and do not confuse it with authorization.
